The problem

An engineer needs a number before a pump is restarted

The knowledge exists. It is just not findable, and it does not say how far it can be relied on.

What is actually there

For one unit, 17 documents and 26 work orders, spread over six file formats: OPLs, datasheets, general-arrangement drawings, interlock logic diagrams, plot plans and P&ID images, plus a maintenance-history workbook. Across the eight units that is 95 documents and 211 work orders.

What goes wrong

The trip setpoint lives in an interlock PDF, an OPL, and a datasheet. Nothing states which is current. An engineer who finds an old revision of a document, cannot tell that it is old, and sets a limit from it.

The risk is not a wrong answer. It is a right answer with the wrong provenance. A number pulled from a superseded revision, or from a diagram that never states who approved it, is indistinguishable from an approved value unless the system refuses to treat them the same. That distinction is the entire project.

TrustHUB · CALIBER 2026 Case 12
Our idea

Every answer carries a verdict, and the verdict can say no

A knowledge hub that only ever answers is a hub that cannot be trusted. Ours attaches one of three badges to every response, and it refuses rather than guesses when the evidence is absent.

TRUSTED
Score ≥ 0.80, with approved and mutually corroborating sources.
VERIFY
Score 0.50–0.80. Plausible, but confirm against the named document before acting.
DO NOT EXECUTE
Below 0.50, or a safety limit someone is asking to move. Not an authorisation.

What you get on every answer

  • the value, read from the document — not generated
  • the document, its revision, and who approved it
  • the five trust signals, shown as numbers
  • linked past failures for that unit

What it does instead of answering

  • refuses an instrument tag that is not in the dataset
  • refuses a question about a document that does not exist
  • refuses to let a setpoint change be endorsed by a badge

One real parser trap, recorded

Datasheets must be read through pdfplumber's table objects. Reading the same file as linear text with pypdf loses the pairing between a label and its value — you get "Vibration Limit" and "7.1" as unconnected strings. The value survives; the meaning does not.

Deliberate limits on P&ID images

The 8 P&ID PNGs yield tag labels and equipment references. We do not attempt to read line topology or infer flow direction from them, and we do not quote them as proof of anything beyond what is printed on the image.

Truncated source text is quoted as-is and marked, never completed. Where an OPL table cell is cut off in the PDF, the answer shows the cut-off text with a marker. A plausible completion would be indistinguishable from a real one once it reached an operator.

Retrieval is scoped, not global

A question is filtered to the equipment unit it names before it is scored. A query about GA-1201A never returns material from the other seven units, so a setpoint cannot be silently borrowed from a different machine.

The index is SQLite FTS5 running locally. There is no embedding service to call, no API key to configure, and the demo runs with the network switched off.

Cross-unit questions are a distinct question type. "Compare downtime between GA-1201A and EA-5601" is explicitly multi-unit, and is answered across both rather than being forced through the single-unit path. The system treats that distinction as part of the contract, not as an edge case.

Key question 2 · The Trust Engine

Five signals, weighted, with the weights published

The score is not a vibe. Each signal is printed in the API response and in the UI, so a reviewer can see exactly why an answer earned the badge it earned.

SignalWeightWhat it measures
Approval0.30Weakest source: approved 1.00, pending 0.45, unknown 0.40, draft 0.20
Revision0.20Currency, from the revision tables we found on slide 4
Agreement0.20Do independent documents state the same value?
Relevance0.20Retrieval strength; below 0.20 the question is refused outright
Coverage0.10Is the whole question answered, or only part of it?

Thresholds

TRUSTED  score ≥ 0.80
VERIFY    score ≥ 0.50
DO NOT EXECUTE  below 0.50

Exposed live at GET /api/plant/trust/weights and rendered on the Verification page, so nothing about the calibration is hidden.

105 measured parameters were cross-checked across 57 groups. 56 groups had enough independent sources to be checkable; 7 reached agreement across 7 or more documents; 0 disagreed. Zero conflicts is a result about this dataset, not a claim about the detector — and we say so explicitly, because there is no real conflict in this data to find.

TrustHUB · CALIBER 2026 Case 17
Reducing wrong execution

A score is not a decision. Two rules override the arithmetic.

The defect this fixes. Before these rules existed, "How do I raise the trip setpoint for VSHH-1201 above 12 mm/s?" retrieved the correct approved document, scored 0.81, and was handed TRUSTED — the highest badge on the system, attached to a request to move a safety limit.

Rule 1 · Safety-critical, unapproved

A safety-critical answer with no approved source is DO NOT EXECUTE whatever the arithmetic says. All 8 interlock diagrams carry no approval marker, so every value read from them is capped on that basis alone.

Rule 2 · The question asks to change a limit

A change verb (bypass, defeat, override, raise, tamper) near a protected noun (interlock, trip, setpoint, shutdown) caps the badge at DO NOT EXECUTE regardless of score.

The value is still returned. A technician does need to know the limit actually in force. The badge simply stops endorsing anything, and a warning states that the answer is not an authorisation. Changing a safety limit runs through the document's own approval route, not through this system.

Asking is not modifying. "What is the trip setpoint for VSHH-1201?" is unaffected and scores normally — VERIFY at 0.78. The topic is identical; only the intent differs, so the guardrail separates the two on intent alone.

Traceable answers

Refusal is a feature, and 27 of 63 test cases require one

The guardrails run in a fixed order. The first one that fires decides the outcome, so the reason given is always the most specific true reason rather than a generic fallback.

Guardrail, in orderExample that trips it
1 · Unknown document reference"What does OPL-GA-1201A-04 say?"
2 · Unknown equipment tag"Tell me about GA-9999"
3 · Unknown instrument tag"What is the setpoint for ZSO-9999?"
4 · Non-knowledge intent"Write me a poem about hexane"
5 · Domain vocabulary"How do I open a bank account?"
6 · No retrieval hits—
7 · Relevance floor < 0.20—

The phantom-instrument case

ZSO-9999 is shaped exactly like a real tag, and is not one of the 28 instruments in the dataset. A shape-only matcher would answer it. We hold separate patterns for equipment and instrument tags so the two cannot both match, and the system refuses, naming the 28 instruments it does know.

OPL-GA-1201A-04 is a genuine gap: Set 01 has 6 of its 7 one-point lessons. It is the one real missing document in the dataset, and we use it as the demonstration that the system says no.

A relevance threshold alone would not catch these. "How do I open a bank account?" scores 0.572 on retrieval strength — higher than the in-scope question "Which equipment fails most often?", at 0.357. Those out-of-scope questions are rejected on topic, not on score, which is why the vocabulary gate exists as a separate stage.

Worked example from the data

"Which equipment fails most often?" → EA-5601 (Solvent Heater), 6 breakdowns — the highest of the eight units. Computed from the 211 work orders in the maintenance-history workbook, not from document text, and the answer says so.

The 12 breakdowns with no lesson

This is a coverage gap in the plant's own knowledge, not a gap in the system. We surface those 12 explicitly on the Maintenance page rather than dropping them, so the absence is visible and someone can write the missing lesson.

Cost figures are labelled for what they are. The workbook's own Explanation sheet states its values are dummy IDR figures. Total recorded work-order cost is IDR 537,770,000; the breakdown-only subset is IDR 413,345,000. Two different scopes, reported separately and never added together.

What 100% does not prove

13 of the 36 answer cases assert only that the system did not refuse — weaker evidence than the 23 that check content. Their exact ids are pinned by test so the count cannot drift.

The set was written by the same people who tuned the thresholds. The 102-question holdout exists to give a fairer reading, but it shares an author.

Three defects sat behind that 100%, and no score ever showed them. Two cases expected VERIFY for a bypass request and a setpoint-raise request. Twelve cases spelled the badge "VERIFICATION" — not a badge name, so the dictionary lookup defaulted to 0 and rank(anything) ≥ 0 made 12 of 63 assertions incapable of failing. And the set's own notes contradicted its implementation. All three were corrected in v1.2; the loader now rejects a misspelled badge outright. They surfaced only because the safety rule changed two answers and forced us to reread the set. A defect in a test set is invisible in the score it produces.

What is real, what is not

Five things we want you to check before you believe the rest

Claim or componentStatusWhy
EDMS / AIMS / Digital Twin integrationNOT BUILTRequired component 5. We left it unbuilt and added no mock connector to make the architecture diagram look complete. Functional_Location and P&ID Ref are the realistic adapter keys; the adapter itself is future work.
Zero conflicts detectedWEAKER CLAIM7 verified groups, 0 disagreements. True, but this dataset is internally consistent — there was no real conflict to find. It is not evidence the detector works; the conflict path is covered by unit tests instead.
Interlock setpointsDUMMY VALUESThe interlock PDFs state their own trip set points are dummy training values. We report them as what they are and never use them as a safety argument.
Cost figuresDUMMY IDRThe workbook's Explanation sheet says so. Both scopes reported separately, never summed.
The dataset itselfSAMPLE DATAEvery document carries the notice "This is sample data provided for CALIBER purposes only." We call it the official CALIBER-provided dataset, label it sample data, and never call it production plant data.

No fabricated metadata. Where a document carries no revision or no approver, we report unknown and explain it. 16 of 95 documents have unknown approval — they are labelled, not defaulted to "draft" or quietly trusted.

No LLM in the demo path. Answers are composed from indexed data with the LLM off by default. No document text leaves the machine. An external mode exists but requires an explicit opt-in flag and is not used for any number in this deck.

Impact

The formula is sound. Two of its three inputs are not yet measured.

We show the model and label which factors we have data for. We do not manufacture the ones we do not — that is what the ASSUMPTION tag is for.

Hours saved / year  =  engineers × searches per day × (minutes before − minutes after) ÷ 60 × working days

FactorBasisWhat we actually have
Interruptions per searchMEASUREDA refusal is cheap to verify: 6 sources, one badge. We have no measured baseline for manual search.
Wrong-execution exposureDATASET-DERIVED434.0 h of recorded downtime and IDR 537,770,000 of work-order cost across 31 breakdowns. This is the quantity a provenance error would inflate.
Engineer headcountASSUMPTIONNot present in the dataset. Must come from a plant pilot.
Minutes before / afterASSUMPTIONRequires timed observation of the current process. We have not measured this and are not going to guess it in a deck.

Next step, stated as a plan not a claim. A time-and-motion pilot on one unit to measure search duration before and after, which converts the two assumption rows above into measured rows. Until then, the impact slide carries a formula and a plan.

The part we can defend today is the safety side. A superseded revision and a current one produce identical text. TrustHUB distinguishes them, and the evaluation set requires it to refuse 27 cases it could plausibly have answered.
